### Слайд 1. Market Analytics

Здравствуйте. Мой проект — Market Analytics, веб-приложение для анализа ценных бумаг. Ядро расчётов написано на C++, затем портировано на Kotlin, и на Kotlin же сделан веб-сервис. Расскажу, как проект прошёл все шесть этапов: требования, проектирование, ядро, портирование, тестирование и Git.

### Слайд 2. Задача: доходность и риск бумаги за минуту

Задача: инвестору нужно быстро понять поведение бумаги. Приложение само загружает реальные котировки Московской биржи — индекс и крупнейшие акции, а любую другую бумагу можно добавить по тикеру. Оно считает метрики доходности и риска, индикаторы технического анализа и сравнивает бумаги между собой.

### Слайд 3. Шесть этапов — шесть артефактов

Проект прошёл все шесть этапов из задания. Для каждого есть конкретный артефакт в репозитории: документ требований, диаграммы PlantUML, модуль на C++, порт на Kotlin с веб-интерфейсом и хранением в PostgreSQL, набор тестов с отчётом, история Git с CI и запуск через Docker Compose.

### Слайд 4. Требования: 9 пользовательских историй

Требования оформлены как пользовательские истории с критериями приёмки — 9 историй и около 35 критериев. Например, для загрузки CSV: ошибка показывается с номером строки, API возвращает 422. Отдельная история — хранение: бумаги и все запуски анализа сохраняются в PostgreSQL. Плюс нефункциональные требования: работа без интернета, лимит загрузки, защита от обхода путей, запуск одной командой.

### Слайд 5. Диаграмма вариантов использования

Два актора: инвестор-аналитик и разработчик. Анализ включает построение графиков; загрузка CSV включает валидацию; настройка параметров и выбор движка расширяют анализ. Консольная утилита market_cli — отдельный вариант использования.

### Слайд 6. Архитектура: сервис и лаборатория

Архитектура слоистая. Ядро не зависит ни от веба, ни от базы, а оба ядра выдают один и тот же JSON — поэтому Kotlin-сервер может вызывать C++ утилиту как внешний процесс. Данные хранятся в PostgreSQL за интерфейсом репозитория: есть реализация для базы и в памяти, и один и тот же набор тестов проверяет обе. Всё разворачивается двумя контейнерами через docker compose.

### Слайд 7. Диаграмма классов ядра

Модель предметной области: свеча, параметры анализа, отчёт, торговый сигнал, перечисления тренда и зоны RSI. Три модуля: загрузчик CSV, индикаторы и анализатор. Структура одинакова в C++ и Kotlin, отличается только идиоматика языка.

### Слайд 8. Диаграмма классов веб-слоя (Kotlin)

Веб-слой: модуль Ktor с маршрутами, сервис MarketService — каталог, анализ, загрузка и сравнение, — и адаптер CppEngine, который запускает C++ утилиту через ProcessBuilder. DTO сериализуются kotlinx.serialization.

### Слайд 9. Последовательность: анализ инструмента

Сценарий анализа: браузер шлёт GET с параметрами, сервер их проверяет, читает котировки из PostgreSQL и считает на Kotlin или вызывает market_cli. Результат одной транзакцией записывается в историю, а клиент получает JSON с номером запуска, метриками и рядами для графиков.

### Слайд 10. Последовательность: лаборатория C++

Расчёт в лаборатории: Kotlin проверяет параметры, берёт котировки из PostgreSQL, пишет временные CSV и запускает market_cli нужной командой. C++ считает и возвращает JSON со временем расчёта, Kotlin формирует краткий итог и сохраняет результат в таблицу lab_run как JSONB, чтобы его можно было открыть из истории.

### Слайд 11. Проверка CSV и обработка ошибок

Алгоритм проверки CSV построчный: заголовок, число колонок, числа, логика OHLC, порядок дат. Любая ошибка сразу прерывает чтение и сообщает номер строки. В интерфейсе пользователь видит причину — как на скриншоте.

### Слайд 12. ER-диаграмма: схема PostgreSQL

Это реальная схема PostgreSQL, она создаётся миграцией Flyway. Инструмент и его котировки, запуск анализа с метриками, рядами индикаторов и сигналами, сохранённые сравнения с матрицей корреляций. Внешние ключи с каскадным удалением и CHECK-ограничения повторяют правила проверки CSV, так что некорректная свеча не попадёт в базу даже в обход кода. Импорт и сохранение запуска идут в транзакциях.

### Слайд 13. C++ ядро: что и как считается

Ядро на C++17 — около 285 строк логики, в рамках требования 150–300. Оно считает доходность, годовую волатильность, просадку, коэффициент Шарпа, RSI по Уайлдеру и сигналы пересечения скользящих. Консольная утилита пишет отчёт в JSON или в текстовом виде, полный прогон — около 3,5 миллисекунд.

### Слайд 14. Портирование ядра на Kotlin

Ядро индикаторов портировано на Kotlin: логика та же, код на четверть короче — сериализация через аннотацию, функции коллекций, null-safety вместо NaN. Совпадение с C++ проверяется автотестом. Но дублировать функции в продукте смысла нет, поэтому роли разделены: интерактивный анализ в интерфейсе делает Kotlin, а C++ отвечает за тяжёлые расчёты — об этом следующий слайд.

### Слайд 15. C++ квант-лаборатория: тяжёлые расчёты

Чтобы у двух языков были разные задачи, тяжёлые вычисления вынесены в C++. Это бэктест стратегии с перебором параметров и честной проверкой на данных, которых алгоритм не видел при подборе, Монте-Карло для оценки риска и оптимизация портфеля. Здесь важна скорость: 100 тысяч сценариев на год вперёд — около секунды. Kotlin готовит данные из базы и сохраняет результат.

### Слайд 16. Пример: бэктест разоблачает переобучение

Пример работы лаборатории. Лучшая на истории пара скользящих даёт коэффициент Шарпа 2,66 — выглядит отлично. Но на последних 30 % данных, которые при подборе не использовались, та же стратегия даёт минус 1,37 и проигрывает простому «купить и держать». Это классическое переобучение, и программа показывает его наглядно: тепловая карта всех пар, кривые капитала и граница обучения на графике.

### Слайд 17. Веб-интерфейс

Так выглядит интерфейс: слева каталог и загрузка файла, сверху параметры анализа, дальше плитки метрик, график цены со скользящими и маркерами сигналов, ниже — RSI и таблица сигналов. Каждый запуск сохраняется в базе — внизу есть история, любой старый отчёт открывается одним кликом. Свой CSV тоже сохраняется в базу. Есть тёмная тема, а библиотека графиков поставляется локально, так что всё работает без интернета.

### Слайд 18. Сравнение инструментов на демо-данных

Экран сравнения на демо-данных. Данные синтетические — сгенерированы моделью с общим рыночным фактором, поэтому корреляции реалистичные, от 0,24 до 0,43. Видно, что DEMO_TECH дал лучший коэффициент Шарпа, а у DEMO_ENERGY самая глубокая просадка.

### Слайд 19. Тестирование: 170 тестов, 0 падений

Всего 170 тестов: 51 на Google Test и 119 на JUnit с Kotest, все проходят. Отдельно проверено, что бэктест не заглядывает в будущее, а Монте-Карло воспроизводим при одинаковом seed. Тесты хранилища и API запускаются дважды — на хранилище в памяти и на настоящей PostgreSQL, а клиент Мосбиржи проверяется на локальной заглушке ISS API. Покрыты граничные случаи: нулевой и слишком большой период, крайние значения RSI, нулевая волатильность, 18 видов некорректных строк CSV, откат транзакции. Найдено и исправлено восемь дефектов; например, D-02: оба языка принимали шестнадцатеричные числа как цены, а D-06 обнаружился при переходе на базу — несуществующая дата 30 февраля проходила проверку.

### Слайд 20. Git и непрерывная интеграция

Работа велась в Git: отдельная ветка, коммиты по этапам, изменения вливаются в main через Pull Request. GitHub Actions на каждом PR собирает C++ и запускает Google Test, затем собирает Kotlin и запускает JUnit, включая тест паритета. Весь стек — веб-приложение и PostgreSQL — поднимается одной командой docker compose up, а тесты запускаются в контейнере отдельным профилем.

### Слайд 21. Работающее приложение

Итог: проект прошёл полный цикл. Есть работающее веб-приложение на реальных котировках Московской биржи с хранением в PostgreSQL, консольная утилита, разделение ролей: Kotlin — сервис, C++ — квант-лаборатория, 170 тестов, CI и запуск одной командой через docker compose. Развивать можно так: другие стратегии в лаборатории, учёт дивидендов, внутридневные данные и учётные записи пользователей. Спасибо, готов ответить на вопросы.
